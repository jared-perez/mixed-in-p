# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Mixed in P is a desktop application for DJs that:
- Analyzes audio files (AIFF, WAV, MP3, FLAC) to detect BPM, musical key, and energy level (1-10)
- Displays results as harmonic key codes (1A-12A, 1B-12B) or traditional key notation
- Provides batch file renaming with customizable templates, and sidebar drag-and-drop routing between panels
- Converts between audio formats (WAV, FLAC, AIFF lossless; MP3 encoding via lameenc)
- Slices audio files with visual range selection, nudge controls, and playback preview
- Edits metadata tags (title, artist, album, genre, BPM, key, year, track, comment) with auto-save
- Built-in audio player with playlist, transport controls, drag-to-reorder, and four collapsible sections below it: Waveform, Zoomed Wave, Loop Slicer and a metronome (tap tempo, time-bend, a three-way click choice — silent / standard tick / sharp beep — and a Global Click toggle, on by default and persisted, that keeps it sounding on other panels)
- Interactive keyboard panel with 3-octave piano, harmonic key strip reference, and chord playback (two views: hex grid and circle of fifths)
- Sidebar drag-and-drop: drop files onto nav buttons to route them to any panel
- Pipeline: per-panel triangle toggles pick which of rename → convert → analyze a run performs, mirrored by three minis in the header beside the target playlist. Start Pipeline in any enabled panel runs that panel's files through the later enabled steps and files each track into a chosen (or newly created) playlist

## Tech Stack

- **Language**: Python 3.11+
- **GUI**: PySide6
- **Audio Analysis**: librosa (BPM/key detection), soundfile (I/O)
- **Audio Encoding**: lameenc (MP3 encoding)
- **Audio Playback**: sounddevice (keyboard panel tone generation)
- **Metadata**: mutagen (ID3 tags, supports read/write/delete)
- **Packaging**: PyInstaller

## Common Commands

```bash
# Virtual environment
python -m venv venv
source venv/bin/activate  # Linux/Mac
venv\Scripts\activate     # Windows

# Install dependencies
pip install -r requirements.txt

# Run application
python -m src.main

# Run tests
pytest tests/
pytest tests/test_analyzer.py -v  # Single test file

# Build executable
pyinstaller mixedinp.spec
```

**The shell here is zsh, not bash.** `${PIPESTATUS[0]}` — the usual guard
against a pipeline reporting the *last* command's status — is a bash array and
expands to **empty** in zsh, printing a bare `EXIT=` with no error, so the guard
silently does nothing. zsh spells it `${pipestatus[1]}` (arrays are 1-indexed).
This matters most for pytest, whose totals line is easy to pipe through `head`
or `tail`: that reports **tail's** exit code, and a run with real failures has
already looked like `exit 0` here more than once. Redirect to a file and read
`$?` on the very next line instead:

```zsh
venv/bin/python -m pytest tests/ -q > /tmp/out.log 2>&1; echo "EXIT=$?"
tail -3 /tmp/out.log; grep -cE "^(FAILED|ERROR)" /tmp/out.log   # 0 = clean
```

## Key Domain Knowledge

### Harmonic Key-Code Mapping

The key-code system maps musical keys to codes for harmonic mixing:

| Code | Minor Key | Code | Major Key |
|------|-----------|------|-----------|
| 1A   | G#m/A♭m   | 1B   | B         |
| 2A   | D#m/E♭m   | 2B   | F#/G♭     |
| 3A   | A#m/B♭m   | 3B   | C#/D♭     |
| 4A   | Fm        | 4B   | G#/A♭     |
| 5A   | Cm        | 5B   | D#/E♭     |
| 6A   | Gm        | 6B   | A#/B♭     |
| 7A   | Dm        | 7B   | F         |
| 8A   | Am        | 8B   | C         |
| 9A   | Em        | 9B   | G         |
| 10A  | Bm        | 10B  | D         |
| 11A  | F#m/G♭m   | 11B  | A         |
| 12A  | C#m/D♭m   | 12B  | E         |

Compatible keys for mixing: same number (relative major/minor) or +/-1 on same letter.

## Technical Considerations

- **BPM ambiguity**: Electronic music often has tempo that could be read as half/double (64 vs 128). Default to DJ-typical range (90-180 BPM).
- **Key detection confidence**: Show confidence scores and alternative suggestions; allow manual override.
- **Key notation modes**: Supports both key codes (1A-12B) and traditional key notation, toggled in Settings.
- **MP3 encoding**: Uses lameenc at 320 kbps default. Lossy-to-lossless upsampling is explicitly blocked.
- **Conversion quality only ever goes down, and "same format" is not the rule — "never upwards" is.** Two predicates in `src/conversion/result.py`, applied to the *same* rule from opposite ends. Between two formats, equal settings are the whole point (the everyday container change), so only `raises_quality` is refused — with an `error`, the same class of refusal a lossy source gets, because the user asked for something they will not get. Into the format the file already has, equal settings would merely rewrite it, so it takes `is_quality_downgrade` — a strict drop in rate and/or depth (96 kHz/24-bit FLAC → 44.1 kHz/16-bit FLAC, for older CDJs) — and anything else is `skipped`. MP3 is exempt from both: its axis is the bitrate, and `_convert_to_mp3` ignores rate/depth entirely. Three call sites must agree or a row reads "Ready" and pressing Convert does nothing (or errors): `convert_file`, the CLI dry run (planned/skipped/blocked), and `ConversionPanel._verdict` (status text + which files are sent). Things a naive comparison gets wrong. Compare the **effective** bit depth (`effective_bit_depth`), because FLAC clamps a 32-bit request to 24 and an 8-bit one to 16 — so "24-bit FLAC → 32 bit" is a no-op rewrite, not an upgrade, and asking the writer for one thing while testing another is how the two drift. A **None** setting means "keep the source's" (what the CLI passes when the flag is omitted) and must read as neither direction. And an **unknown source answers False to both**, so an unmeasurable file is neither rewritten on a hunch nor pre-blocked — it fails, or succeeds, on its own merits. Note the Sample Rate / Bit Depth combos now change a row's *status*, not just the output, so they refresh the table the same way the format combo does. **"Keep source" (`None`) is what makes that rule liveable** and is the first entry in both combos: it leaves an axis alone, so a mixed-rate batch converts at each file's own quality and a source below the lowest offered rate (an old 22.05 kHz rip) is not stranded with every choice an upsample. Three things `None` broke on the way through. The panel's `start_conversion` is `Signal(list, str, int, object, object)` — a `Signal(int)` delivers `None` as **0** silently, and `int(combo.currentData() or 44100)` did the same thing by hand. `load_config` needs `_optional_int`, because a bare `int()` raises on a JSON `null` and a missing key (an older config) must still take the default rather than reading as "Keep source". And `bit_depth=None` hands the **source's own subtype** to the writer, which the containers do not all accept — FLAC has no FLOAT, DOUBLE, PCM_32 or PCM_U8, so a 32-bit float WAV (what a DAW exports) failed outright — hence `_storable_subtype`, which asks `sf.check_format` and steps down to the widest PCM subtype that fits without ever widening. Adding the option also widened the selectors, and `WindowSizer._min_width_for("convert")` was a **constant**: the row overflowed and the longest label was clipped instead of the window growing (`visual_pass` caught it in fr and it). It now measures `ConversionPanel.format_row_min_width()`, which sums the lossless controls whether or not they are showing — hidden widgets contribute nothing to a layout's hint, so asking the row would shrink the minimum the moment MP3 hid them.
- **The rename→convert→analyze→playlist pipeline carries two spellings of every path, and a hook placed at "the last line" of the analysis writer never runs.** `TrackStore.add_from_path` stores `str(path.resolve())` and `get_by_path` compares exactly, so an `AnalysisResult.file_path` comes back **resolved**, while the library keys on `normalize_track_path` — and on macOS the two differ for anything under `/var`, which is where every test's `tmp_path` lives. A set built from the converter's output strings therefore matches nothing on macOS and everything on Linux/Windows, so `PipelineRun.awaiting_analysis` is a **dict** from store spelling to library spelling, keyed on what a result will actually wear (`main_window._pipeline_analyse` takes `track.file_path` *after* the add, never the path it passed in). The per-track hook belongs in `_update_track_from_result` because that is the one point every completed track passes exactly once (the progress signal takes most, `_on_analysis_finished` sweeps the rest) — but that method **returns early under the session write-freeze**, so appending the hook to its end silently skips a frozen run. The writes moved to `_apply_analysis_result` and the hook wraps it. Three more things the shape forces. A run with nothing to convert must **skip the thread entirely**: `ConversionWorker.run` with zero files emits `error` and no `finished` (`conversion_worker.py:64`), so the run would wait for a signal that never comes — and the same-format rows are forwarded on purpose, because a batch already in the target format would otherwise leave the button dead and the feature unusable. The add must **never prompt**: it runs from inside an analysis progress signal with the next result queued behind it, so `resolve_additions` takes `policy=SKIP` for `ASK` — the pile-up `_flush_open_batch` already forces `allow_duplicates=True` to avoid. And `_track_id_for` reuses an existing library row **without re-reading its tags** (deliberate — an inline edit must not be rolled back), so the row is patched from the result afterwards; that covers a WAV (nowhere to keep BPM/key), a frozen session, and a passthrough file the library already knew, and is a no-op otherwise since only non-None fields overwrite.
- **A step that can be skipped turns every "and then" into a question, and three of them were written as statements.** The pipeline grew per-step toggles (rename / convert / analyze, mirrored by three minis in the header beside the target); the sequence is fixed and the toggles only choose members, so the engine holds the enabled set as a **snapshot taken at arming** — a toggle flipped mid-run must not re-route a batch already in flight — and `ConvertPipeline.next_step(after)` is the whole of "flow through the later enabled steps only". What broke was every place that already *knew* what came next: `_start_conversion`'s zero-file branch and `_on_conversion_finished` both called `_pipeline_analyse` outright, so an Analyze-off run went to the analysis it was told to skip. They ask `_pipeline_advance` now. Three more the shape forces. **The playlist is not a step and has no toggle** — it is where every run ends — so Analyze-off needs a direct-add leg (`awaiting_add`), which retires per path like an analysis rather than draining once like `passthrough`, because each add commits on its own. A run reaching its Convert step **presses the panel's own button** (never a second arming path — every invariant lives behind `_on_convert_clicked`), so it arrives at `_start_conversion` looking exactly like the second Start that the re-arm guard exists to refuse: `_pipeline_entering_convert` is what tells the run apart from its own successor. And a **no-op rename must bypass `_start_rename`**, which returns silently at zero renames — the run would then wait for a thread that never started; it is retired straight from the engine after one Yes/No question, because a rename that changes nothing is a reasonable thing to ask for when the later steps are the point.
- **`blockSignals` silences everything the signal drove, including the widget's own housekeeping.** The reflect half of a two-place control sets the state inside `blockSignals(True)` so the mirrors cannot echo — and `PipelineToggle` hung its tooltip off `toggled`, so a *reflected* toggle changed its picture and kept the other state's sentence: clicking a header mini lit its panel triangle while it went on offering to switch the step on. Anything a widget must do for *itself* on a state change belongs on Qt's own hook — `checkStateSet()` for a `QAbstractButton`, which fires however the state was set — never on the signal a caller is entitled to block. Two things made it read as a stranger bug than it is. It is invisible to any test of `toggled` (the signal genuinely was not emitted, correctly), and the one panel that reads its own state from config at construction, where nothing is blocked, looked **right** — so one missing call presented as three panels disagreeing with each other, and "fiddling with them" fixed it because a direct click is unblocked. Found in the running app, not by the suite.
- **A control that appears in two places needs one owner and two reflects, and the field it writes must then leave `_persist_config`'s merge list.** Each step toggle shows in its panel *and* as a mini in the header. MainWindow holds the state: both widgets emit a *request*, both are reflected from it with `blockSignals`, and neither writes config. That last part is not optional and it inverts the standing rule two entries below — the merge list exists so a **panel**-written field is re-read from disk before a wholesale save, so a field the *window* owns must be off it, or `self._config.pipeline_rename_enabled = True; self._persist_config()` overwrites the value with the disk copy on the very line that saves it. Note the older coupling died with the same edit: auto-analyze used to drag the pipeline about in four directions, from when the pipeline was a Convert feature that could only end in an analysis. It drives its own analysis (`_pipeline_analyse` calls `_start_analysis` whatever the setting says), and the proof was a test that **passes against the unmodified old code** — the coupling was already vestigial, so decoupling it was a deletion rather than a change.
- **An editable combo whose list and whose text mean different things must have its completer turned off.** The pipeline's target field reads a *picked* item as "use that playlist" and *typed* text as "create one", which are not the same act — and Qt's default inline completion silently converts the second into the first the moment the typed name matches a listed one, retargeting the run at somebody else's playlist with no gesture from the user. `setCompleter(None)`, and `pipeline_target()` reports a pick only when `currentIndex() >= 0` **and** the item's text equals the edit text. The other half is the restore: a remembered name is stored as the **name**, not a node id (an id means nothing once its playlist is deleted), and must be put back with `findText` → `setCurrentIndex`, never `setEditText` alone — that is the "one new numbered playlist per launch" bug in one line. It also has to be restored **twice**: once in `PipelineCluster.__init__`, where the list is still empty and the name can only be typed back, and again from `MainWindow` once the real playlists have been fed in, which is the pass that can resolve it. The field lives in the **header**, not in a panel, because it belongs to the run rather than to a step — a run that skips Convert entirely still ends in a playlist.
- **WAV cannot hold BPM or key, and the write layer says it can**: `update_bpm_key` returns `True` for a WAV and discards the value, so an analysed WAV looked exactly like an analysed MP3 with none of the detected data kept — there is no failure to detect at write time. Ask `stores_tags()` (`src/metadata/tags.py`) instead, which answers from the extension. `TAGLESS_EXTENSIONS` is only `.wav`, established by round-trip: FLAC, AIFF and MP3 all read back what was written. Analysis of a WAV is still allowed on purpose — the BPM/key readout and the rename are useful on their own — so the Analyze panel flags the row rather than blocking it.
- **A burst that outgrows its detector reads as several bursts, and every assertion downstream then lines up against the wrong beat.** The metronome's sharp voice became a 40 ms beep (a 5 ms tick is too short for the ear to integrate *or* to carry a pitch, so it has nothing to cut through a track with — 40 ms at 2-3 kHz is 17 dB more energy at the same peak, and both ends are raised-cosine ramped or the tone's own hard edges are two extra clicks). What broke was `tests/test_metronome_engine.py::onsets`, which segmented the click train by comparing each hot sample to the **last onset** rather than to the **last hot sample** — correct only while every burst is shorter than `min_gap`, which the tick was and the beep is not. One beep became five onsets 400 samples apart, and `min(accented) > max(plain)` failed with numbers that look like a lost accent rather than like a mis-segmentation. Two things the fix has to keep in mind: a sine's sub-threshold notches at its own zero crossings are under a sample wide and its ramped fade-out tail is ~75, so both stay well inside the gap either way; and a **beep's onset is detected a few samples later than a tick's** — later still at 2 kHz than at 3 kHz, because a threshold is crossed sooner by the faster wave — so a grid assertion across a voice change is measured per stretch, with a tolerance of one attack ramp, and it is the onset *count* that catches a lost or doubled click.
- **Windows file locking**: mutagen file handles must be released before rename operations. The rename worker includes retry logic for transient Windows file locks.
- **Cross-platform paths**: Use `src/utils/app_dirs.py` for all persistent data (config, history). Never hardcode OS-specific paths.
- **Every path entering the app goes through `normalize_track_path`** (`src/utils/paths.py`): library identity is exact-string (`Library.add_track` keys on `WHERE path=?`, `duplicate_policy.filter_new` compares literals), so two spellings of one file mean two rows and a duplicate check that cannot see the collision. The Windows trap that proved it: `QUrl.toLocalFile()` **and** `QFileDialog` return forward slashes there (`C:/music/a.mp3`) while `find_audio_files` and argv return backslashes. Normalize at the point a path arrives from the OS or the user — a drop handler, a dialog result, argv, a `QFileOpenEvent` — and **never** on a path read back out of the database, where the stored string *is* the identity and rewriting it on load breaks row lookup, the playing-track marker and relocate.
- **PyInstaller**: Use `sys._MEIPASS` for bundled resource paths when frozen. See `_get_base_path()` in `src/gui/app.py`.
- **Panel routing**: sidebar drag-and-drop (drop files onto nav buttons) and table drag-out. The "Send To" dropdowns that also did this were removed with the step toggles; their `send_to_*` signals and MainWindow receivers survive as plumbing for a possible CLI, emitted by nothing.
- **A new column in the library database needs an ALTER, not just a schema edit**: `_SCHEMA` is run with `CREATE TABLE IF NOT EXISTS`, so an existing `library.db` keeps its old columns and a fresh install gets the new ones — the two diverge silently until a query hits the missing column. Add the column to `_SCHEMA`, add the `ALTER TABLE` to `Library._migrate` (keyed on `PRAGMA table_info`, not `user_version`), and bump `_SCHEMA_VERSION`. Dry-run it against a copy of the real database before shipping. A whole **table** needs none of this: `_init_schema` runs `executescript(_SCHEMA)` on *every* open, so `CREATE TABLE IF NOT EXISTS` reaches an existing database exactly as it reaches a fresh one (v7's `discogs_releases` and `discogs_path_releases` added no migration branch at all). It is only a new column on an existing table that `CREATE TABLE IF NOT EXISTS` silently skips. Two different migration triggers, on purpose: a **column** is keyed on `PRAGMA table_info` (a version check would skip a database touched by a build predating the pragma bump, and re-adding a column is unrecoverable); **stored data that needs recomputing** is keyed on `user_version`, which also keeps it one-shot.
- **A persisted enum named for what a thing *looks like* goes stale the moment the look changes — and swapping two such names is a migration with no safe trigger.** The Player's two tunnels shipped as `wormhole` (a wireframe closed loop) and `tunnel_chase` (generated ahead in beat-space). When the second one's wall became nebula cloud it was plainly the wormhole-*looking* of the two, so the **labels** had to trade places. The ids were **retired rather than swapped** — `loop_tunnel` and `beat_tunnel`, names for the *mechanism*, which is the thing that does not change — and that is precisely what makes `config._renamed_vis_mode` safe: it keys on the stored value still **being** a retired name, so it is one-way and **harmless to re-run**, the same shape as `_folded_vis_mode` beside it. A straight swap has no such trigger, because both names are valid before *and* after: it would need a version counter, and a second pass — or a crash before the first config save — would silently flip the user's setting back. So the labels now read **crossed against the ids on purpose**, and the menu comment and both module headers say so. Three things that made it cheap. A rename migration must map the id the user picked to whatever renders **the same picture** today, never to whatever inherited its old label — that is the one bug here that would hand every existing user the other visual, so it gets a test run against a map pointing the wrong way. **Swapping labels costs nothing in i18n** as long as both source strings survive verbatim, because lupdate keys on source text: all eleven `.qm` files came out **byte-identical**, which is the check to make rather than an assumption to state. And when sweeping identifiers, `\btunnel_chase\b` does **not** match inside `vis_tunnel_chase` or `backdrop_tunnel_chase` — `_` is a word character, so there is no boundary there. Both survived the sweep and were caught only by grepping for survivors, never by trusting the substitution count. **The cheap case is the mirror of this one, and it is worth naming so it is not treated as expensive: a look-named *label* sitting over a mechanism-named id renames for free.** Silly Scope → **stream** (2026-08-26) touched a module name, a class, a render-mode id, an attribute and one `tr()` string, and needed **no migration at all** — because the only value config ever stores for it is `backdrop_scope`, the *menu row's* id, which names the slot rather than the picture and did not move. `stream` is a `RENDER_MODES` id reached only through `_BACKDROP_VIS_MAP`, i.e. derived on every launch and never written down, so a plain substring sweep was safe where the tunnels' needed a one-way migration and a test pointed the wrong way. Two mechanical notes. A bare `silly_scope` → `stream` substring replace is *correct here* and does the compound names in the same pass (`vis_silly_scope` → `vis_stream`, `_silly_scope` → `_stream`, `test_vis_silly_scope` → `test_vis_stream`) — the opposite of the `\btunnel_chase\b` trap above, and the same fact about `_` being a word character is what makes both true. And the prose is the part a sweep cannot do: `silly scope` appears in sentences where the replacement is not word-for-word ("the silly scope was only ever a backdrop" → "the stream was only ever a backdrop"), so grep for the human spelling separately and read each hit.
- **Two records of one fact drift; the fix is one read path with a precedence rule, not two writers kept in step.** The Discogs release memory is per *file*, and a file need not be a library row — the Metadata panel deliberately takes a drop without importing it, so a lookup there was applied and forgotten in the same gesture. That wants a second, path-keyed store (`discogs_path_releases`) beside `tracks.discogs_release_id`, which is precisely the shape that rots. `Library.release_for_path`/`remember_release_for_path` are the only door: the **row wins when it has an answer** (it survives a rename and a path cannot), the path table answers only for a file the library has never heard of, and a write goes to exactly one of them — never both. The case that makes it hold is the **promotion**: a file whose release was remembered before it was ever imported, then imported, would otherwise be answered forever by the weaker record, and adding it to a playlist would silently lose the release the user approved — so a read that finds a row with no release and a path record moves the value onto the row and deletes the path record. Note the *identity* and the *description* are separate on purpose and stored differently: the identity is per file and permanent, the description is per release, replaceable, and cached as **JSON rather than columns** because its field set is the provider's to change and nothing queries it — a schema migration per displayed field is a bad trade, and `Candidate.from_release_facts` tolerates absent and unknown keys so the set widens for free.
- **Making a field *searchable* is `_FTS_COLUMNS` plus a data migration**: the index statements are generated from that tuple (every name is also a `tracks` column), so adding one covers create/insert/update/resync in one edit — `_ensure_fts_schema` notices the column list changed and rebuilds `tracks_fts`, since an FTS5 table's columns are fixed at creation. What it does NOT cover is `search_blob`, the LIKE fallback's haystack: rows written before the change have a stored value their blob predates, so bump `_SCHEMA_VERSION` and call `_rebuild_search_blobs` (the `comment` addition was exempt only because a blank field can't change a blob). Rewrite a blob only via `_indexed_from_row` — the one call site that spelled the fields out by hand (`relink_track`) is exactly the one that broke when the tuple grew.
- **A stylesheet that targets `::item` defeats the model's `BackgroundRole`**: `app.qss.template` has a `QTableView::item` rule (only padding and border, but that is enough), and once a stylesheet styles items Qt paints their background itself and ignores the brush returned from `data()`. Returning a colour for `BackgroundRole` therefore drew *nothing at all* — while every assertion on `data()` passed, because the model really was returning it. Paint it in the item delegate instead (`_NoFocusDelegate.paint` in `analysis_panel.py` fills `option.rect` before `super().paint`, skipped while selected so the selection still reads), and **test it by sampling a render** — `viewport().grab().toImage().pixelColor(...)` — since a data-level test cannot see the difference. Ten of them passed against a row drawn identically to an untinted one.
- **Bare `QWidget` containers are opaque**: `app.qss.template` opens with a global `QWidget { background-color: @BG_DARK@ }`, so any plain `QWidget` (or `QStackedWidget`) used purely as a layout container paints `BG_DARK` over whatever panel it sits on. Give such a container an object name and a `background-color: transparent` rule. `QStackedWidget` is also a `QFrame`, so it inherits the global 1px frame border too — add `border: none` unless a box is wanted. See `#sidebarModeStack` / `#playlistTreePanel`.
- **Moving a layout into a widget changes its spacing**: a nested layout inherits the parent layout's spacing; a widget's own layout falls back to the Qt style default (6px, not `Theme.SPACING`'s 8). Call `setSpacing(Theme.SPACING)` explicitly when wrapping an existing row in a container.
- **A drop that must not delete the source sets `CopyAction`**: outgoing drags from the Player/Analysis/Convert tables remove their rows when the drag returns `MoveAction`. Any drop handler that keeps the source intact must call `event.setDropAction(Qt.DropAction.CopyAction)` **before** `event.accept()` — see `PlaylistTree._drop_tracks` and `ReorderableTableWidget._handle_internal_reorder`. Forgetting it silently turns "add to playlist" into "move out of playlist".
- **Qt draws its drop indicator only for a drag the *model* accepts, and refusing the mime type does not stop the drop from working** — which is how a view ends up with a fully functional reorder and no visual feedback at all. `QAbstractItemView::dragMoveEvent` sets `dropIndicatorRect` inside `if (canDrop(event))`, and `canDrop` ends at `model->canDropMimeData(...)`, which for a `QStandardItemModel` is a mime-type check that `NODE_MIME` fails. But the *position* is computed earlier, in the `dropOn` call `canDrop` makes on the way — so `dropIndicatorPosition()` stays correct for a handler that forces its own verdict, the drop lands where it should, and the rect that would have been painted is never assigned. The playlist tree therefore paints its own (`PlaylistTree._node_drop_marker`, drawn in `paintEvent` beside the track-drop outline that already existed for the same reason). Three things the shape forces. **One function computes the plan for both the feedback and the drop** (`_node_drop_plan`), or the line is a second opinion about where the node goes and drifts from the first. **A drop that will be refused must show nothing and `ignore()` the move event**, so the cursor says no — the old code accepted every `NODE_MIME` drag and let `dropEvent` silently decline a folder dropped into its own subtree, which reads as a dead drop rather than as a rejected one. And the append-at-root line takes its **y from the bottom-most visible row and its x from the root indent**: the bottom row may be a folder's last child, and a line at *that* indent claims the node is going into the folder. Note `visualRect` answers null for a row the name filter hid, so the walk skips hidden rows rather than trusting the last model row. Test the marker's *pixels* (`viewport().grab()`), never just the attribute — an attribute the view was never told to repaint reads back perfectly.
- **The tree's own drags carry file URLs too**: a playlist dragged in `PlaylistTree` ships both `NODE_MIME` and its member tracks' URLs (one gesture reorders internally AND exports to Finder). Every drop handler must therefore check `NODE_MIME` **first** — treating such a drag as a file drop makes a playlist merge itself into whatever it lands on.
- **A drag out of a *derived* list must carry no `SOURCE_PAGE_MIME` at all.** The marker means "internal panel drag", and every target then routes it through `DRAG_ROUTES` — where an unrecognised source has no routes, so the drop is refused **everywhere** rather than falling back to anything. Omitting it makes the drag indistinguishable from a Finder drop, which is exactly right for a list that owns no rows: `CompatibleTracksPanel` is a query result, so there is nothing to move *out of* and a Move would ask a source to give up a row it never had. `compatible_panel.drag_mime` builds the payload on its own (URLs only, `exec(CopyAction)`) instead of calling `start_file_drag`, and a test asserts the marker's absence so it reads as a decision rather than an omission.
- **`isVisible()` is False for every widget on a panel that isn't the current page** — it answers "is this on screen", not "is this switched on". `PlayerPanel.compat_panel_min_width` keyed off it and reported 0 (i.e. *no* extra window width needed) whenever another panel was showing, which is precisely when the window sizer asks. Key such state off the control that owns it — the toggle's `isChecked()` — and in an offscreen test, where nothing is ever shown, assert `isHidden()` instead.
- **The Player writes the visible list's tags through to the library on every list change**, so a library row tagged behind its back is blanked by the next add. `_persist_playlist` passes each `PlaylistEntry`'s fields to `add_track` **even when empty** (deliberate: entry fields mirror the file's tags, so clearing a tag clears the row) — and an empty string is not `None`, so it overwrites. Consequence for tests: put fixture tags on the entry dict handed to `add_tracks`, never on the library row afterwards, or the second file added silently strips the first one's key.
- **`QDropEvent` keeps only a raw pointer to its `QMimeData`**: in a test, `view.dropEvent(make_event(QMimeData()))` lets Python collect the mime object and the first `event.mimeData()` call segfaults. Hold the `QMimeData` in a local for the event's lifetime.
- **Concurrent lazy imports abort the process**: a main-thread `read_metadata` (mutagen → charset_normalizer) racing a decode thread's lazy librosa import produces `Fatal Python error: Aborted` with both threads inside `<frozen importlib._bootstrap>`. In tests, warm the imports up front — `tests/gui/conftest.py::warm_lazy_audio_imports` does librosa for every GUI test, `test_playlist_drag_add.py::warm_tag_reader` does the tag reader. Any test that pumps the event loop while a Player fixture is alive can trigger it, because pumping is what lets a queued prefetch actually start decoding. This signature is NOT the known interpreter-teardown segfault, which happens after every test has already passed.
- **A modal opened from inside a drop or drag handler fights Qt for the mouse grab**: fire it from `QTimer.singleShot(0, …)` instead, and accept the event first. Both the moved-file warning (`player_panel._guard_drag`) and the duplicate-tracks prompt do this. Consequence for the caller: the add is *pending*, not done, when the handler returns — so anything that must run afterwards goes in the continuation, and the accept/ignore verdict can't depend on the outcome. Accepting early is safe only because these drops are `CopyAction`, so a cancelled add leaves the source untouched anyway.
- **A panel that starts reader threads must join them on close**: `stop_playback()` ends the audio output, not the *readers* — a decode or render in flight is one long blocking call with nothing to cancel, so the only option is to wait. `PlayerPanel`/`SpectrumPanel` expose `shutdown_workers()` (built on `thread_keeper.wait_for_threads`), called from their own `closeEvent` and from `MainWindow.closeEvent`. Skipping it means `QThread: Destroyed while thread is still running` (undefined behaviour) and a worker emitting into a deleted receiver.
- **A panel that starts worker threads must also *forget* them when they finish**, and must never call into one it has only a stale name for. `_art_thread`/`_art_worker` were assigned and never cleared, so a later scroll called `cancel()` on a wrapper whose C++ object `deleteLater` had already destroyed — `libshiboken: Internal C++ object (ArtworkThread) already deleted`, thrown from a line that looks perfectly safe. Clear the attributes from the thread's `finished`, but **only if a newer request has not already replaced them** (the previous worker finishing is the normal case when a new one cancels it, and an unguarded clear wipes the live one's references), and guard any call into a possibly-dead worker with `shiboken6.isValid`. This is the sibling of `thread_keeper.keep_alive` above: that stops the *wrapper* being collected too early, this stops the *attribute* being used too late.
- **`font-size` in QSS must go on the widget selector, not a sub-control, if anything measures `widget.font()`.** `QHeaderView::section { font-size: … }` is honoured when the section is painted — the header visibly grows — but never reaches `header.font()`, and `SeparatorHeaderView._title_font()` derives from exactly that, which is what the playlist's word-fit column widths are measured with. The result was a larger header word in an unchanged, too-narrow column. Use `QHeaderView { font-size: … }`. Related: **row height does not follow the font either** — rows sit at the vertical header's `defaultSectionSize` and nothing re-measures them, so scale that explicitly. `resizeRowsToContents()` is the tempting fix and the wrong one: it sizes to the delegate hint *plus* the QSS `::item` padding, which took the playlist from 30px rows to 51px **at the size everyone already uses**, i.e. it redesigns the app for users who never touched the setting. **A column width written as a constant is an English width.** The Player's optional columns shipped at 70–80px and six of the eleven languages opened one clipped (ru `Номер трека` wants 97 of Track #'s 70; ja wants 95 for both `ビットレート` and `アートワーク`) — while the columns beside them, sized from their own header word with the header font, were fine in every language. So a fixed width is a *base*: `_BASE_COLUMN_WIDTHS` plus `_apply_header_fit_floor`, recomputed from the base each time rather than raised in place, so a smaller text size gives the width back. Test it as "the default is at least the measured fit", never as a pixel count — under the suite's missing stylesheet the English `Track #` measures 71px against the app's 57, so an equality assertion is a true statement about a header the app never paints. **How you measure "the fit" depends on who paints the label, and the two headers in this app differ.** The Player's `SeparatorHeaderView` blanks the style's text and draws its own at `_TEXT_PAD`, so its width is `QFontMetrics(_title_font()).horizontalAdvance(label) + 2 * _TEXT_PAD`. The Analyze table is a plain `QHeaderView` where the *style* draws the label, and three things it accounts for are invisible to a `QFontMetrics` call: the QSS `QHeaderView::section` padding, the `font-weight: bold` from the same rule (which never reaches `header.font()` — see above), and the room Qt reserves for the **sort indicator on every section** when sorting is enabled, which is 28px of the 44 that separate "Energy" (46px of text) from its 90px section hint. So there, use `header.sectionSizeHint(col)` and do no arithmetic of your own (`AnalysisPanel._fit_header_widths`). That header is additionally **centred with `ElideNone`**, so an over-long word is cut at *both* ends with no ellipsis to admit it — `Энергия` rendered as "нерги", which reads as a word rather than as damage, and its columns are `Fixed` so the user cannot drag them wider. English was clipped too (the `y` of "Energy", the `e` of "Key Code"), which is the only reason anyone noticed.
- **A size derived from a row height must never be read back off the row height.** The playlist's artwork is scaled from the row (`_art_strip_height`), and the Full artwork view then sizes the *row* from the art — so reading `verticalHeader().defaultSectionSize()` for the band feeds the calculation its own output and every pass over the setting grows the rows again, without bound. One source both derive from instead: `PlayerPanel._text_row_height()`, computed from the captured `_base_row_height` and the text preset and never read back from the header. Test it by applying the setting **twice** — a single application is stable in the broken build too. **The Metadata panel's cover column is the same law with a different mechanism, and the mechanism matters.** A `QLabel` holding a pixmap reports *that pixmap* as its size hint, and the pixmap was scaled from the label's own width — so it converged at 132px inside a 225px column on the first pass and could never grow again, which is the margin everyone could see. Making the size an **input** (`ArtworkWidget.set_column_width`) is the fix; deriving it from a `sizeHint()` override is not, and this is the trap: turning on **word wrap** makes a widget report `hasHeightForWidth`, and a parent layout then asks `heightForWidth(w)` and **ignores `sizeHint().height()` entirely** — the box sat at the label's 120px minimum with a 142px cover drawn into it while every hint in the chain said 150. So `setFixedSize` from numbers the parent chose, and floor any text dimension with `QFontMetrics.boundingRect(..., TextWordWrap, ...)` measured against the *string*, never asked of the label, which answers for the picture whenever there is one. Two siblings from the same feature, both silent: a thumbnail cache keyed on the scaled edge alone cannot tell Top from Middle (identical sizes, different pixels), so the setting appears to do nothing until the key carries the view; and a layout that grows for a column's contents has to shrink again when that column is **hidden**, or a plain text playlist wears three-row rows for artwork nobody can see.
- **A height written as a row count is a *text*-row count**, the vertical twin of the English-width entry above. The Player pins the playlist while a slice view is open so the panel can grow past the viewport and scroll; that pin was `_ROWS_VISIBLE_WHEN_SLICING = 12`, correct while a row was the height of its text and silently wrong the moment Full artwork made a row 78px — 12 of those is 983px against a 793px viewport, so the playlist alone was taller than the panel and the transport, the waveform and the slice controls all opened *below the fold*. The user's report was "I have to scroll all the way down to see what I just opened". A pin that has to leave room for something else is a **budget**: `viewport − _height_outside_playlist()`, capped at the old row count (so a text-height row is pixel-identical to before) and floored at `_MIN_ROWS_WHEN_SLICING` (so a short window shrinks the playlist rather than deleting it). Four things that decide whether it works. Reserve **both** sides — reserving only what sits below the table left the title row unaccounted and the waveform 59px under the fold, which reads exactly like the original bug. Sum **`sizeHint()`, never laid-out heights**: this runs to *decide* a geometry, so the geometry it would read back is the one it is about to replace, and a hidden widget's height is stale garbage (the now-playing label reports 480px while hidden). Recompute on **resize**, because a budget denominated in viewport is wrong the moment the window moves. And in a test, `mapTo` positions are lazy — call `content.layout().activate()` rather than waiting a fixed 20ms, which passes alone and fails under a full-suite load. Its ceiling is real: below the floor no height satisfies both, so a test asserting the canvas stays on screen at *any* window height demands what no implementation can deliver — assert the floor there instead.
- **A decay written per frame is a duration only at one frame rate**, the third of the "a number that is only right in one context" family above, and the one that reads as *tuning* rather than as damage. Tunnel Chase runs its popout at 16 ms while every other visual and the playlist backdrop run at 33, so `0.97 * bass_att` (the kick pulse's average), `0.82` (the star glow's release) and `_VIS_DECAY_FRAMES = 60` ("2 s") all meant something different depending on which host was asking. Express the constant in **seconds** and raise it to `interval / reference` at the point the host announces its rate (`VisRenderer.set_frame_interval`, `BeatClock.set_frame_interval`, `TunnelChaseScene.set_frame_interval`), and pin it with a test that feeds the *same second of audio* at both rates and asserts the state matches. Note the frame count is also a **duration** in disguise: `_VIS_DECAY_MS = 2000` divided by the live interval is the same 60 frames at 33 ms and correct at any other. And the interval is not free to change per mode without saying so — `VisRenderer.frame_ms()` is what the popout's timer reads, while the backdrop deliberately ignores it, because *its* cost is the host: repainting the playlist rows behind the frame measures ~11 ms on its own, so 60 fps there would spend two-thirds of a core redrawing rows nobody asked for.
- **A control loop that measures drift will read its own convergence as drift.** The beat clock corrects the tempo from how fast its phase offset is walking; on the first few seconds that offset is walking from zero to wherever the beat actually is, which is an order of magnitude faster than any real tempo error — so a **correct** 128 BPM tag was driven to 126.8 (the ±1 % clamp, hit from the wrong side) and the lock settled a tenth of a beat off the kick. Two guards, both cheap: don't sample until the thing has been settled for longer than its own settling time (`_ADAPT_SETTLE`, one histogram time constant), and reset that counter on any **step** change (a sticky lock moving to a new bin is a step, not a drift). The symptom is diagnostic — a loop that ends up *pinned to a clamp* is being fed a signal it was not designed for, not merely mistuned. Separately, a gain copied from a prototype is a gain measured on that prototype's *inputs*: 0.3 left a standing ±0.27 BPM limit cycle here and 0.15 settles, which no unit test would have shown, only a 90-second trace printed every ten seconds.
- **A hard clamp on a signal that drives a shape is a square-wave generator, and every downstream term then amplifies its corners.** The stream visual is a garden hose: the *source* moves (today by three weighted drivers — a beat-grid dance choreography read off the renderer's BeatClock, whose kick flux + tick the stream now pays for alongside the beat tunnel; a mid-high "melody" wobble from bands 8-15 of the heights the renderer already computes; and the original band-passed loudness wiggle as texture) and that displacement advects across the window, so the silhouette is smooth by construction and there is no per-edge turbulence machinery at all. Four things that shape forces, each of which shipped wrong first and was found by rendering a still and looking at it. (1) The nozzle was `clip(gain * (fast - slow), -1, 1)`. Loud music sits *on* that clamp, so the history filled with flat tops and near-vertical transitions; the centerline slope reached **6 px per px**, and the surface's pitch term flipped sign pixel to pixel down every wall. `tanh` instead — the limit is the same, the corners are not. (2) The fake normal's x-gradient is deliberately scaled by `0.2 * width` (~240 at this size) so the sheet keeps its side glints, which means it multiplies the centerline's **second** difference by the same 240 and paints it as fine vertical corduroy over the whole ribbon. That curvature was not noise — at 20 history bins a second and the original 10 s crossing, one bin was ~6 px (the crossing has since been retuned to ~0.5 s and the bin rate doubled to 40, keeping a bin inside the smoother's kernel) and the signal genuinely turns over that distance — so the fix is a real smoother, done with three cumsum box passes because the kernel it needs would be a hundred 1-2-1 passes — and now expressed as `_CENTER_SMOOTH_SECONDS`, **seconds of signal** converted through the flow speed, because it shipped as a width fraction and a fraction of the width is a duration only at one flow speed: by the second flow retune (~1.7 s crossing) it covered 0.03 s of signal instead of the 0.18 s it was tuned at, every crest wore a visible corner, and doubling the history bin rate did not touch it because the kinks were the *signal*, not the knots. (3) A bin rate expressed in bins per second is **not** rate-independent on its own: the value pushed was whatever the nozzle held at the end of whichever frame crossed the boundary, so a 33 ms host read it up to 33 ms late and a 16 ms host up to 16, and on a fast attack the two disagreed by more than the wiggle they were recording. Interpolate to the boundary. (4) A sphere put through the sheet's shader is wrong twice over — the curvature term shreds a tiny radius into speckle, and a chrome ramp maps every one of its bands across a 12 px bead as a hard horizontal stripe — so the droplets were **stamped sprites** with a plain lit gradient; the 2026-08-26 tune-up then retired the droplets entirely (next to the sheet they read as clutter, not as beat) in favour of a whole-frame flicker — which blinked the picture without making the stream *carry* the beat, and was retired the same day for the mechanism that does: the kick brightens what is **leaving the nozzle** (`_BEAT_FLOOR`/`_BEAT_PEAK`/`_BEAT_RELEASE_TAU`), stamped into a second history and advected by the same per-column sampling as the centerline, so a beat is a bright surge travelling down a dimmer resting stream. Brightness multiplies the shade only; the alpha belongs to the silence fade, so the silhouette never pulses. And the one that no test could have caught: the ribbon looked *motionless* against a real track while the state under it was moving exactly as designed, because an 11 % swing inside a 42 %-thick ribbon is not a wave — **a wave's amplitude is only meaningful as a ratio to the thing that carries it**, so `_SWING_FRAC` and `_BASE_HALF_FRAC` are tuned as a pair, against decoded audio, never separately against synthetic band heights.

- **Changing a *default* layout reaches nobody who has ever opened the app**, because a saved state always wins — so such a change needs a version and a one-time migration, not just new constants. `PlayerPanel._COLUMN_DEFAULTS_VERSION` against `AppConfig.player_column_defaults_version`: below it, the saved state is discarded once, the shipped layout applied, and the new version **written back immediately** — not left to the next column change, or a user who never touches the header is migrated on every launch and each one eats the session before. Three things that make it survivable. The default order is a **visual** arrangement (`_DEFAULT_COLUMN_ORDER`, applied with `moveSection` left to right before any restore), never a renumbering: logical indexes are the addresses in every saved state in the wild, so reordering the declarations would re-point every existing user's widths at the wrong columns. The version joins `player_column_state`/`player_column_count` on `MainWindow._persist_config`'s merge list — a new field beside one already there and not added to it is reverted on close, which here means migrating forever. A migration that stamps a version is also **not safe to run half-written**: launching the app from the checkout while the field was mid-edit wrote a config claiming a migration that had only partly happened (the new order applied, four of the ten default columns still off), and nothing afterwards could tell it from a layout the user had arranged — the repair was a further version bump. And the tests for the *old* shorter-state path (`_normalize_header`) must now opt out of the migration by stamping the current version, or they discard their own fixture and pass while testing nothing.
- **A default that a saved layout can override needs a user-facing way back**, or the only route to it is a version bump — i.e. a new build, for something the user should be able to do themselves. `PlayerPanel.reset_columns_to_defaults` (Reset Columns, at the bottom of the header menu) restores the shipped order, open set and widths in one click. It re-applies a **width to every column, not just the hidden ones**: a hidden section reports width 0, so a reset that only flips the flag brings a column back at whatever it last held, which for one restored from an old state can be 0 — visible and still invisible. Note what is *not* true here, because it looks like it should be: the order of un-hiding versus setting the width does not matter, measured both ways. That was a comment asserting a trap until a mutation test refused to fail against it.
- **A saved `QHeaderView` state is only safe for the column count it was saved from, and Qt will not tell you.** Adding a column (Player optional columns, §W2-7) taught three things in one item. (1) `restoreState` **accepts** a shorter state — returns True, applies the sections it knows — and what happens to the ones it has never heard of is unspecified and observably inconsistent: a bare `QTableWidget` has them **un-hidden**, this panel's header keeps the flag. So store the count alongside the state (`player_column_count`) and apply default visibility for anything beyond it *after* restoring, trusting neither behaviour. (2) A header that has swallowed a shorter state is left internally inconsistent and the state it then **saves cannot be restored at all** — so the first launch after an upgrade writes a poisoned layout and the second throws it away, taking the user's widths with it; `_normalize_header` re-seats it (snapshot → known-good state → re-apply widths/hidden/order). (3) `MainWindow._persist_config` keeps a **merge list** of fields the panels own and re-reads them from disk before writing its startup snapshot back on close — a new field that belongs with one already on that list must be added to it, or closing the window reverts half a value. Symptom of all three: nothing wrong on the launch that caused it.
- **A single-instance claim must be an OS primitive that is exclusive *by contract* and released by the kernel when the process dies** — a named mutex on Windows, `flock` on POSIX (see `single_instance.py`). `QLocalServer` is the **transport only, never the claim**, on either platform: a Windows named pipe permits many servers on one name so a second `listen()` on a live name *succeeds*; and although a POSIX bind really is exclusive, there is a window where a primary has *created* its socket file and is not yet accepting, during which a connect is refused **identically** to a file left by a crash — so code that probes, sees the refusal and calls `removeServer` to clear the "stale" file unlinks a **live** primary's socket and each loser evicts the last. A refused connect cannot distinguish "dead" from "not ready yet" and the recovery for one is fatal to the other, so never guess at liveness; `removeServer` is only safe while holding the claim, which is the one place it is called.
- **Verify concurrency fixes with `python scripts/race_check.py`, don't reason about them.** Three separate single-instance designs looked correct, passed their unit tests, and gave *every* process electing itself primary the moment five started together — on both platforms, by different mechanisms. The script launches the real `src.main` (not a stand-in), redirects app data so it can't touch a real library, and passes only when exactly one process became primary, every file reached Scratch, **and** Scratch is in `shell_sorted` order. Two related habits it taught: a harness that *models* the component under test will hide the bug (a synthetic primary has its event loop running, while the real one spends ~500ms in `MainWindow()` with none); and always re-run a regression test with the fix removed, because a timing-based test for a platform-specific race is silently vacuous on the other platform — assert the invariant instead.
- **A multi-file "open" is not one call, and its arrival order means nothing.** Windows spawns **one process per file** for a multi-select (measured: five files, five processes, 25–43ms apart, `MultiSelectModel` does not change it) and macOS sends one `QFileOpenEvent` per file, so a batch reaches `MainWindow.open_files` as several calls in a racing order — different on every run. It therefore buffers for `OPEN_BATCH_MS` (300) and acts once, in `_flush_open_batch`, which sorts with `shell_sorted` (natural, filename-only, case-insensitive — what both shells show) and plays row 1. Two things that look optional and are not: the timer is **started, not restarted**, or a trickle of arrivals postpones playback indefinitely; and the *sort alone* is not enough, because without the wait the app has already committed to playing whichever process won the race. Raising the window stays immediate — a bare relaunch means "show me" and has no batch to wait for.
- **Becoming the *default* handler is opt-in, and the two platforms are not symmetric** (`src/utils/default_app.py`). macOS has an API (`LSSetDefaultRoleHandlerForContentType` via ctypes, no PyObjC) — guarded by a check that the process's own bundle identifier is `com.mixedinp.app`, because a handler is named by bundle and without the guard a source checkout hands every audio file to Python.app. Windows has none: `UserChoice` is hash-protected, writing it gets the association reset and looks like malware, so the button opens `ms-settings:defaultapps?registeredApp<Scope>=…` and the user confirms — with `<Scope>` **read** from whichever hive holds our `RegisteredApplications` value (HKLM → `Machine`, HKCU → `User`), never hardcoded. And **there is no readable "are we the default?" on Windows 11**: with our exe demonstrably launching, `assoc` said Windows Media Player, `UserChoice` said ZuneMusic and `UserChoiceLatest` had a hash and no ProgID, so `is_default()` answers `None` (unknowable) and the UI offers the action rather than a state. The macOS content-type list must stay equal to `LSItemContentTypes` in `mixedinp.spec` — LaunchServices silently refuses a type the bundle does not declare; a test asserts the two match. **The macOS write is asynchronous and `LSCopyDefaultRoleHandlerForContentType` is cached per process**: verified by hand, every call returned `noErr` and the plist really changed, yet the same process read the *old* handler back for seconds. So never confirm a set by reading it back (it reports failure for a change that worked), and never write a set-then-restore test — the two races itself and strands a type on the wrong app.
- **Any edge-triggered Qt signal can fire before its receiver is attached.** This bit three times in one module, each found only after fixing the one below: `readyRead` (on Windows it fires before `nextPendingConnection()` returns the socket — drain on take, *and* take a last read on `disconnected` before dropping); `newConnection` (a connection accepted between `listen()` and wiring the slot — wire the receiver **before** listening, then drain the queue once by hand); and an app-level signal emitted during startup, before the window that answers it exists (buffer and replay — `SingleInstance.start_delivering`, `FileOpenRelay.go_live`). The failures are silent and on the *success* path: the sender's write completes into the pipe buffer, so it reports success for a file that is then discarded.
- **`deleteLater` on a child plus `deleteLater` on its parent is a double-free waiting for an event loop**: whichever destroys the parent takes the children with it, and the child's stale delete lands on freed memory — surfacing as a segfault in whatever runs *next*, not where the bug is. Flush with `QCoreApplication.sendPostedEvents(None, QEvent.Type.DeferredDelete)` (post order: children first) rather than leaving it to a loop that may never come round again, and make any drop/close path idempotent.
- **`add_tracks` leaves a file open, and only *one*** — `_prefetch_default_target` warms the selection, else row 0. On Windows that read handle blocks the file from being deleted or renamed (`WinError 32`) for as long as the decode runs. A test that deletes the file it just added is racing that thread: it must call `PlayerPanel.wait_for_readers()` first (`tests/gui/helpers.py::unlink_when_released`). Two traps in diagnosing this: it is invisible on POSIX, where an open handle does not block an unlink; and it looks like a *teardown* problem because it only reproduces in a full run — but the contention from other tests' decodes is merely what widens the window, and the thread belongs to the failing test itself. The tell is which tests flake: those deleting the **first** file of a playlist, never the second. The user-facing version (rename a track mid-prefetch) is already covered — `rename_worker` retries `PermissionError` 3× at 0.3s, and the measured lock is 10–20ms.
- **`python scripts/visual_pass.py` before a release**: a translated label that overflows its widget still passes every assertion about its text, so this renders all twelve languages offscreen and diffs required-vs-allocated width per widget against English. Three things it taught. **Persist the language to config, don't just install the translator** — the sidebar shrinks one Russian label based on `load_config().language`, so a harness that skips that step invents six sidebar defects that do not exist. **Because it persists, it must isolate its own app data** — it redirects `HOME`/`%APPDATA%` at import for itself and every child (the same trick as `race_check.child_env`). This was once a documented manual prefix, and a documented manual precaution is one you will forget: run it bare and it leaves your real Settings on whichever language went last, so the app launches in Korean (`ko` sorts last) until someone works out why. Isolation also fixed what it *measures* — inheriting a real config meant inheriting the developer's saved window geometry, which is why it reported 46 findings against one machine's window size and reports 12 against the shipped default. And **report as a diff against English, not absolutely**: English alone measures ~24 findings that are metric jitter, which would bury the real ones. Ground-truth anything it flags against a screenshot before acting — its padding estimates produce occasional false positives (`プレイリスト` was reported 22px over and renders fine). **A clean run is not coverage**: it measures only *visible* `QLabel`/`QPushButton`/`QComboBox`/`QCheckBox`/`QRadioButton`, so a `QLineEdit` placeholder, a `QHeaderView` section, a tooltip, and anything behind a collapsed control or a hidden column are all invisible to it — **and it walks the app in its shipped default state**, so a label a setting *changes* is never measured at all: the three panels' Start Pipeline labels only exist with a step toggle on, and the run is clean because it saw Convert/Analyze/Apply Rename instead. Measure such a label by hand against the same rule (font metrics + `BUTTON_PADDING`), and remember `font-weight: bold` from the QSS never reaches `widget.font()` — Russian's `Запустить цепочку` is 155px of the 160px minimum once the bold is counted, and 8px narrower if it is not — and it reported zero findings on a batch whose new column headers clipped in six languages. Measure those by hand for any string that lives in one. **It no longer models a `QComboBox`'s chrome with a constant, and nothing else should either**: a 48px `COMBO_ARROW` (font metrics + padding + arrow) is only right for combos wearing the default rule, so the Convert selectors — which carry a tighter one — were reported clipped in four languages while rendering in full, and a pt_BR combo had been a standing false positive. It asks `sizeHint()` now, the style's own arithmetic over the widest item and whatever padding actually applies, which travels to any stylesheet and any platform. **The baseline is a moving number, so establish it rather than quote it**: it was 12, then 11, and is **17** as of the metronome's move into the Player (2026-08-26), whose two extra findings — ja `▸ メトロノーム`, ko `▸ 메트로놈` — are the *same* documented false positive as the four the Waveform / Loop Slicer header split (`0f58fb1`) added before it, and for the same reason: they are the same `section_header` button, whose padding is 0. Ground-truthed by rendering the header in all seven flagged languages — every label clears its own width by 8-15px, and it cannot clip by construction, since `header_button` sizes from the font metrics of the very string it paints. That whole family is `BUTTON_PADDING = 32` false positives (it flags English itself at +18px against buttons whose QSS padding is 0 — ground-truthed by rendering the real window in six languages, every label fits with 5–13px to spare; asking the style for `SE_PushButtonContents`, the same move already made for combos, would take the run to 9). A written-down baseline goes stale the first time someone ships a wider label, and then every later run reads as a regression nobody caused — so before acting on a count, `git stash` and run it again. That comparison takes a minute and is the only thing that says which findings are yours.
- **A cancel flag checked only between work items can never cancel the last one** — and "the last one" includes the *only* one, which is how this shipped looking like "Cancel does nothing with a single file, but works with two". `AnalysisWorker` tested its flag at the top of the per-file loop, so a cancel during the final file fell through to `finished` and the run reported success; the two-file case only appeared to work because the cancel landed during file 1. Gate the terminal signal too, not just the loop entry, and discard the in-flight item's result — a file abandoned partway has nothing worth keeping. **A cancel stops the remaining work; it does not undo what already finished**, so the cancelled path owes the completed items the same follow-through as the finished path: `_update_track_from_result` had already written BPM and key tags as each file landed, but only `_on_analysis_finished` ran auto-rename, so cancelling left those files tagged and un-renamed — a half-applied result nobody asked for. `ConversionWorker` had the identical bug plus no `cancelled` signal at all, and the Convert panel's Cancel button was never connected to anything, so it was dead in every state.
- **`TrackState` is not just a status, it is which panel owns the track.** One `TrackStore` backs Analyze, Rename, Convert and the queue, and each panel filters it by state: `QUEUED` **is** the Rename panel's working set (`rename_panel` lists exactly `get_by_state(QUEUED)`, and `_add_files_to_rename` *re-queues* a track precisely to move it there), while the Analyze table shows `PENDING`/`ANALYSING`/`ANALYSED`/`ERROR`. So a state change is a panel move: cancelling an analysis used to reset its unfinished tracks to `QUEUED`, which silently emptied them out of the very list the user was watching. Cancel leaves them `PENDING` — still queued in Analyze, still visible, still re-runnable. Before widening any panel's filter, check which panel already owns that state.
- **A filtered `QAbstractTableModel` cannot inherit `TrackTableModel`'s incremental updates.** The base keys `dataChanged`/`beginInsertRows` off `_get_row_for_id`, which indexes the **unfiltered** store, while `AnalysisTableModel` overrides `rowCount`/`data` to read `_get_filtered_tracks()` — so every row number it emitted was for a different row, and a state change that moved a track into or out of the filter was announced as a repaint of a row the view did not agree existed. The visible symptom was mild (Status never updated until something forced a full reset, so `ANALYSING` — assigned nowhere, styled and counted everywhere — was invisible), the latent one is not. Override the handlers to a filter-aware `refresh()` that resets when the row count moved and emits `dataChanged` when it did not, and keep the cached count in step in *every* path that resets. Test this on the **signals**, not on `rowCount()`: `rowCount()` recomputes the filter on each call, so it reads correctly even when the view was never told, and an assertion on it passes against the bug.
- **Cancel latency in analysis is one HPSS call, and no amount of checkpointing changes that**: `librosa.effects.harmonic` inside `_rank_keys` measured **5.6 s of a 6.3 s** warm analysis of a 4-minute track — ~97% of the file, in a single uninterruptible library call. Cooperative checkpoints (`should_cancel` → `check_cancelled`, `src/analysis/cancellation.py`) are still worth it, because the one in front of the key stage turns an early cancel into a 6.2 s saving and stops a batch before it starts another file, but a cancel landing *inside* HPSS waits it out. So the UI does not wait for the worker: `_cancel_analysis` disconnects the thread's signals, reports Cancelled at once, and lets the orphaned thread unwind with its results discarded — verified end-to-end, the late `finished` no longer overwrites the cancelled state. Two traps. **Profile warm, not cold**: a first run charges page-cache and numba JIT to whatever stage runs first, which made `detect_bpm` look like 1.48 s when it is really 0.14 s and pointed the fix at the wrong stage entirely. And `AnalysisCancelled` must be **re-raised** ahead of every broad `except Exception`, or a cancel is reported to the user as a corrupt file. Note `closeEvent`'s join budget was 3 s against a >5.6 s HPSS call, so quitting mid-analysis destroyed a running `QThread`; it is `_ANALYSIS_JOIN_MS` now.
- **`QLabel` never elides — it just draws past its own edge.** Use `ElidedLabel` (`src/gui/widgets/elided_label.py`) for any single-line text whose length you do not control, and note it deliberately defers to Qt when `wordWrap()` is on, because `theme.set_description_wrap` toggles the panel hints between wrapping (wide) and one clipped line (narrow). A `QPushButton` is worse: it *centres* rather than elides, so an over-long label is cut at **both** ends — size those from font metrics plus the stylesheet padding the native size hint cannot see (`_fit` in `history_panel.py`, `_fit_buttons` in `dialogs/duplicate_policy.py`). **On a small fixed-size button that padding does not merely crowd the label — it deletes it.** The global `padding: 8px 16px` inside a 24px square leaves no contents rect at all, so the Discogs tab's `→` was **not drawn**: an empty box, which reads as a placeholder rather than as damage, and is invisible to every test and to `visual_pass`. Any button sized below the padding needs its own rule zeroing `padding`/`min-width`/`min-height` (`#discogsApplyButton` in `app.qss.template`, kept there rather than inline so the palette tokens stay in one file) — and the only way to know is to render it and look.
- **Which end an `ElidedLabel` gives up depends on the value, not the widget**, so the mode is a constructor argument and `set_elide_mode` can switch it per value. A **path** is cut from the left: its tail is the folder actually chosen, and every path on the machine looks alike down the root — measured in the Convert destination, where ~150px of room renders `/var/fol… masters` under `ElideMiddle` and `/var/folders/nh/m4f…` under the default, against `…44.1k 16bit masters` from the left. Prose still elides right. Two things about its tooltip. It is maintained **only in `resizeEvent`**, so a caller that sets text which must stay recoverable sets the tooltip itself at the same time (`metadata_panel._load_file`, `ConversionPanel._sync_destination`) — new text at an unchanged width can start overflowing with no resize to follow. And do **not** move that into a `setText` override to be clever: it silently overwrites the tooltip those callers deliberately set, and the attempt at it displaced the `setSizePolicy(Ignored, …)` line every instance in the app depends on to be shrinkable at all. The Metadata panel's tooltip test is what caught it; the suite was otherwise green.
- **An inline `setStyleSheet` on a widget is half of the rule the stylesheet would have given it**, and the missing half is always a state. The review dialog's Apply carried `background-color: NEON_YELLOW; color: #000000; font-weight: bold` inline, which is `#primaryButton` minus `:hover`, `:pressed` and — the one that mattered — `:disabled`. So a disabled Apply stayed as bright and bold as a live one, and pressing it did nothing; that is the *ordinary* state of the cover search when the release has no scan, so the commonest outcome looked like a broken button. The hardcoded `#000000` is the second half of the same mistake: `theme.py` ships four palettes and the light one does not want black text on its accent. Give the widget the **object name** and let `app.qss.template` own every state and every token. The inverse also holds — a rule that must not leak into a sibling belongs inline or under an object name, never on the bare type (see `#historyLimit`).
- **A redraw whose steps read each other's widgets must be ordered, or the first one answers from the last pass.** `_apply_result` runs `_fill_rows` then `_fill_artwork`, and `_fill_rows` ends by syncing Apply against "is anything on offer" — including the artwork row, which `_fill_artwork` has not drawn yet. On the first pass that row is still the hidden one `_setup_ui` built, so a result offering a **cover and no field changes** — every tag already matching the release, i.e. any file tagged from Discogs in an earlier session — left Apply disabled over a sleeve the user could plainly see. The fix is to re-sync at the end of the step that changed the input, not to reorder the two (reordering swaps which one is stale). The tell is that the state is correct after any *second* redraw, so a candidate switch repairs it and only the freshly-opened dialog is wrong.
- **A result carries what *this* request asked for; it cannot rebuild a list the *previous* request produced.** A candidate switch in the review dialog is answered by a fetch of one release — `LookupThread._run_job` sets `candidates = [job.candidate]` when a job names one — so the dialog, which rebuilt its switcher from `result.candidates` on every `set_result`, collapsed to a single disabled row the first time it was used. The escape hatch for a wrong match worked exactly once, on both panels that offer it. The ranked list belongs to the **search**, so it belongs to the dialog, and `set_result` leaves it alone. This is the same family as the two-records entry above and the one the handoff calls out — *a path that reuses an object built by another path inherits only what that path filled in* — and the suite could not see it for the same reason: the fixture handed `set_result` a full candidate list, which is the well-populated shape no caller actually produces. **Ask of any such test whether its input is the one the code really receives.**
- **An `ElidedLabel` that responds to the mouse wants the opposite defaults from one that just reads**, which is what `HuggingElidedLabel` (`player_panel.py`) is. Three inversions, all found on the now-playing line once the "In Playlist" link joined the filename there. (1) `setSizePolicy(Ignored, …)` makes it *fill* its layout share, so a stretchy one measured **684px wide around 157px of text** — five hundred pixels of clickable nothing that opened a playlist. Give it `Maximum` and put the slack in a trailing `addStretch`. (2) `Maximum` alone then makes it **unshrinkable**, because `QLabel.minimumSizeHint` answers the full text width — so the eliding silently stops happening and the label goes back to shoving its neighbour off the panel. Floor `minimumSizeHint` yourself; that floor is what lets the cap bite. (3) The tooltip rule *replaces* the tooltip on every resize, so a deliberate one ("Drag this onto a playlist…", "Open the playlist…") is deleted the first time the window moves — remember the caller's and **append** the cut-off text to it. Note that inverts the standing warning one entry above against a `setText` override; it is safe only because this subclass owns both ends of the rule.
- **A cap is what keeps a row inside the viewport — not the layout**, in any panel whose content scrolls horizontally. The Player's rows are explicitly allowed to be wider than the viewport (`_sync_title_row_width` says so), so two labels that hug their own text do not compete for a share of the row: they *widen the content* and answer a long filename with a horizontal scrollbar under the whole panel. `_sync_now_playing_widths` caps the filename at a share of the viewport and hands the link the remainder, so each elides at its own cap. Two things it has to do that a resize handler alone would not: the terms are `sizeHint()` and the viewport, **never a laid-out width** (it runs to decide the geometry it would read back), and it is re-run from `_update_now_playing` because a **new track changes the split with no resize to follow**. And do not test the split against pixel counts — the suite has no stylesheet, so measure it as "the label is at its cap" / "the link is its own hint".
- **`QLayout.spacing()` reads back as `-1` when it was never set**, and any width computed as `sum(hints) + spacing * gaps` then *subtracts* where it meant to add. `ConversionPanel.format_row_min_width` was understating its row by ~64px (nine gaps at the style's real 6px, minus the nine it took off), which stayed invisible while the row had slack and produced a clipped `44,1 kHz (CD)` with the arrow over the text the moment the row filled up. Set the spacing explicitly on any layout you intend to measure — which a layout handed to a widget wants anyway, since it otherwise takes the Qt style default (6px) over `Theme.SPACING`. Related, in the same method: a **size hint ignores `setFixedWidth`** (the 34px icon buttons hint at 54), so cap each contributor at `min(sizeHint().width(), maximumWidth())`.
- **Styling a sub-control stops Qt drawing the arrow inside it, and the CSS triangle that replaced it does not work.** `QComboBox::drop-down` and `QSpinBox::up-button`/`::down-button` each carried a width and a background, which makes Qt's stylesheet engine own that sub-control — so the style's own chevron is no longer painted and an explicit `::down-arrow` rule has to supply one. That rule used the **web-CSS triangle trick** (`width: 0; height: 0` plus a thick top border and transparent sides), which the engine **does not implement**: it fills the sub-control box with the border colour. Every combo in the app therefore wore a small grey **rectangle** where its arrow should be, and every spin box wore two grey squares — which the user reported as "a little folder icon that looks like I can select it", i.e. as an icon rather than as a control. Deleting only the arrow rule is **worse than either**, and this is the part that makes the bug hard to back out of: a styled `::drop-down` with no arrow rule draws **no arrow at all**. Both halves have to go together, and then the platform draws a real chevron on every style and every palette for no asset and no code. An image would have been the alternative, and it could not have been a committed one — `theme.py` ships four palettes with different `CHROME`. Two knock-ons worth knowing: `#compactCombo` cannot keep a `::drop-down` override without bringing the rectangle back (it keeps its padding, and most of its saving with it), and every combo's `sizeHint()` **shrank 6px**, taking `ConversionPanel.format_row_min_width()` down 18px in en/de/ru — the native sub-control is about half the 30px the old rule reserved, so the "reserved twice" problem in the entry below is largely gone with the rule that caused it. **You cannot see any of this from the QSS or from a test** — it was found by rendering a combo and looking at the pixels, and confirmed by rendering all three variants side by side.
- **The combo keeps that rule; the spin box had to break it, because "let the platform draw it" is only an answer while every platform draws it acceptably.** QMacStyle draws a `QSpinBox`'s stepper over the **border** box, so it paints out the right-hand edge of the frame — the yellow focus ring stops dead where the stepper begins, which reads as a half-drawn box — and its arrows are hairline chevrons at this control height ("only a dot for the symbol"). Windows 11 draws two proper **side-by-side** triangles and looks right, so one control disagreed across the two platforms, and the user reported it as a Mac bug rather than a style difference. Styling the sub-controls is what fixes both, since the frame is then ours and nothing native paints over it — which means supplying the arrow, and the entry above is exactly why that was refused before: the CSS triangle fills the box, and a committed image cannot work because `theme.py` ships four palettes. So the image is **generated per palette at stylesheet load** (`styles/spin_arrows.py`, one PNG per direction per state, at 1x/2x/3x because Qt picks the `@2x` sibling of a stylesheet image on a scaled screen), cached under the app data dir by **colour** so a palette change writes new files instead of reusing a stale picture. Four things the shape forces. The paths are substituted like any palette token, and if generation fails `load_stylesheet` **drops the whole block between the markers** — the fallback has to be the platform stepper, because a styled sub-control with a *missing* image draws nothing at all, and an empty box is worse than an ugly one. `:off` (Qt's "this end of the range is reached") and `:disabled` get a **dimmed** arrow rather than `image: none`, so a spin box at its limit still reads as a spin box. The `padding-right` that reserves room for the arrows is stated **twice** — the app sheet and the Settings panel's own inline `QSpinBox` rule, whose `padding` shorthand overrides it — so a test compares the two rather than trusting them to be kept in step; and every width capped with a constant (`setMaximumWidth(120)`, `setFixedWidth(80)`) had to be measured instead, since the cap now pays for the arrows as well as a translated suffix. And **none of this is visible to the suite or to `visual_pass`**: both run offscreen, which resolves to Fusion, where the native stepper was already fine — a rendered assertion there passes identically against the broken build. It was ground-truthed by rendering a real `MainWindow` under QMacStyle, QFusionStyle and QWindowsStyle and looking at the pixels.
- **A `QComboBox` styled by QSS reserves the drop-down twice**: `padding-right: 30px` *and* `::drop-down { width: 30px }`, and Qt adds the subcontrol width to the size hint on top of the padding. Measured, that is **70px of slack over the widest item** on every combo in the app — 105px of hint for a combo whose longest entry is `FLAC`. Where a row is tight, `#compactCombo` (`padding-right: 4px`, a 22px drop-down) reclaims ~35px each with the width still decided by text metrics, so it holds in every language; it bought the Convert destination its place on the format row. Do not instead cap a combo's width with a constant — that is an English width, and a combo clips rather than elides its current item.
- **A combo's padding is also the popup's, and only the closed box looks right.** On any style whose combo popup is a *menu* — `SH_ComboBox_Popup` is 1 on both QMacStyle and QFusionStyle — the popup is sized from the combo's **frame** rather than from its items, so it opens ~16px narrower than the combo, and each row then spends ~29px more on the check column beside the current item. The combo's own width is `widest text + padding + arrow`, so that padding is the slack the popup borrows. `#compactCombo` (entry above) cut `padding-right` from 30px to 4px for the Convert format row, which left the closed box fitting its widest item to the pixel and the open one **15px short in all twelve languages** — `Keep sourc`, `24 bit (DVD`, exactly as reported. The Keyboard view switcher, sized from a constant, was short in ru, fr and ja by the same mechanism (`Шестиугольная сетка` → `Шестиугольная сетк`). The fix is `FittedComboBox` (`src/gui/widgets/fitted_combo.py`), which floors the popup at the combo's own width on every open; **every combo in the app is one**, enforced by a test, because a bare `QComboBox` added later would ship cut off. Two things that make the *modest* rule the right one. Fitting the popup to its widest item is unbounded — the lookup dialog's release switcher holds free text and would drop a screen-wide menu out of a 400px control. And **asking the popup's delegate what a row reserves gets an answer the style does not honour when it paints**: QFusionStyle claims 51px of menu chrome, draws its text at the left edge like any list, and would have been handed 36px of dead margin for a popup that was already correct — while QWindowsStyle answers a third way again (`SH_ComboBox_Popup` 0, a list delegate, no chrome). A width a style *claims* is not the width it *paints*, and only rendering it tells you which. **Nothing automated sees any of this**: the suite is Fusion, where the popup already comes out exactly as wide as the combo, so a test that opens one and measures it passes against the broken build; and `visual_pass` measures widgets that are on screen, while a popup is neither a child of the panel nor open when it looks. Ground-truth it by rendering the popup — `combo.view().window().grab()`, which the window's own `grab()` does not include — in every language, against a control with the fix disabled.
- **Reflecting state into a checkable widget re-enters its own handler.** `_sync_destination` calls `setChecked` to *show* the mode, and unguarded that fired `toggled` → `_on_source_toggled`, whose "nothing remembered" branch raises a **modal file dialog** — from inside a state refresh. In the suite that is a hang with nobody to click it; in the app it is a dialog nobody asked for. Wrap the reflect in `blockSignals(True/False)` and let the handler own the acting, never the other way round. The same guard is what lets a cancelled dialog put the toggle back without the revert reading as a fresh toggle.
- **The GUI suite runs with no application stylesheet, so a width assertion written there measures a different app.** `tests/gui/conftest.py` forces the offscreen platform but never calls `setStyleSheet`, so every widget wears Fusion's default metrics instead of `app.qss.template`'s: the same `#treeCreateButton` measures **80px** in the suite and **69px** in the running app. That gap runs the wrong way — a control that clips in the app has room in the test — which is how a test asserting "the create buttons are not clipped" was written, watched to pass, and found to pass *against the clipped build*. Combined with the entry above (a `QPushButton` centres rather than elides, so there is no ellipsis to see), the only honest check for "does this row fit" is to render the real window — `QApplication.setStyleSheet(load_stylesheet())`, build the actual `MainWindow`, `grab()` it and **look at it** — plus `visual_pass.py` for the translated cases. Don't set the stylesheet inside a test to close the gap: it is application-global and would leak into every test that follows. Assert structure there (a constant is small, a widget is icon-only), not pixels. The same blindness applies to *anything* Qt computes lazily from layout: a `QTableWidget`'s vertical scrollbar reports `maximum() == 0` until the pending layout is processed, so a "did it scroll?" guard reads a stale range — and in a passing build the scroll under test is what forces the update, making the guard circular. Show the widget and `qtbot.wait(10)` before reading a scroll position (`settle_at_top` in `tests/gui/test_player_scroll_on_add.py`).
- **`show()` on a child whose parent is hidden does not make it visible, and Qt then behaves differently in ways a test cannot see.** `PlaylistTreePanel().tree.resize(...); .show()` leaves the tree `isVisible() == False`, and in that state a `QStandardItemModel.clear()`-and-repopulate **keeps its scroll position by itself** while a genuinely-shown tree loses it — so a test for "a drop no longer scrolls the tree to the top", written that way, passed identically with the fix removed. The same artefact then argued the *opposite* case: it made `setCurrentIndex` look as though it does not scroll to the new row, which produced a `scrollTo` "fix", with a comment explaining a trap, for something the real view already does. Show the **panel**, not the widget under test (`scrolled_panel` in `tests/gui/test_playlist_drag_add.py`), and settle the conclusion by driving the real `MainWindow` with the fix **and** without it — both wrong answers here survived a green suite and were caught only by that comparison.
- **Loading the stylesheet does not close that gap, because the *style* differs too — and QSS cannot reach it.** The entry above is about `app.qss.template` being absent; this is the axis underneath it, and it survives fixing that one. The offscreen platform resolves to **Fusion**, macOS to the **macOS style**, Windows to a third — and a `QStyle`'s pixel metrics are not stylesheet properties, so no amount of `setStyleSheet` makes them agree. Measured: `PM_FocusFrameHMargin` is **2 on Fusion and 4 on macOS**, which is the space a style reserves *inside* an item's text rect. So **any width written as "font metrics + a constant" is a guess that can be right on at most one platform.** Concretely: a 17px per-cell pad, measured by rendering cells at every width until the pixels matched an unelided reference, was correct under Fusion, green in the whole suite, and ~8px short on the machine the app runs on — every key code in Compatible Tracks drew as `1…`. Neither `QFontMetrics` nor `subElementRect(SE_ItemViewItemText)` sees the whole reservation, so neither is a substitute. **Ask the style instead, through the same path that paints the cell**: `resizeColumnToContents` → `sizeHintForColumn` → `sizeFromContents(CT_ItemViewItem)`, which also folds in `sectionSizeHint` for the header word for free. `CompatibleTracksPanel._measure_narrow_columns` fills the table with every value a column can hold, resizes to contents, then empties it — so the widths legitimately differ per platform (52/50/37 on macOS, 48/46/33 under Fusion) and that is the fix working, not drift. Four corollaries. **A fixed column over a closed set of values must fit the widest member of that set**: it cannot be resized, so an ellipsis there hides a value with no gesture that recovers it — size it so elision never happens, and leave `ElideRight` on as the visible symptom if that ever breaks (`ElideNone` cuts the tail silently instead). **Measure the whole domain, not a representative** — widest is not longest, `A#m` beats `12B`, and `render_key` answers in whichever of three notations Settings is on, without rebuilding the panel. **Make the domain closed rather than assume it is**: BPM is three digits only because `_bpm_cell` rounds for display, since the library stores it as a `REAL`. And **test it as `sizeHintForColumn(col) <= columnWidth(col)`** — two numbers the active style supplies, so the assertion travels to whichever style runs it, and it fails under Fusion too against a hand-written pad.
- **A pixel-diff over a `grab()` is in *device* pixels while `visualRect` is in logical ones**, and on a Retina screen that harness reads the top-left corner of the cell and calls a fully clipped value identical to an unclipped one. This is how the checker written to prove the entry above reported the *visibly* clipped build as fine — twice, on the strength of a number rather than a look. Multiply by `img.devicePixelRatio()` when indexing a grab, give any such check a **control that must fail** (force the old width; if it still passes, the harness is broken, not the build), and render the thing and **look at it** before believing either answer.
- **Every expand in the playlist tree writes straight to the database**, so any expanding the *code* does must be suppressed on the way past `_on_expansion_changed`. The tree stores each folder's open/closed state on every toggle (that is what makes it come back the right shape next launch), and it already flags its own replay with `_restoring_expansion`. The name filter (§5) then added a second source of programmatic expansion — revealing a match force-opens its ancestors — which without a flag rewrote the user's stored shape as they typed, so quitting mid-search brought the app back wearing the filter's idea of which folders were open. Hence `_filtering`, checked alongside `_restoring_expansion`, plus a snapshot of the *view's* expansion taken before the first keystroke and restored when the box closes. Two related facts about that filter: it is `setRowHidden` only, because manual order is the truth here and there must never be a sort or a proxy; and `_rebuild` re-applies it, since a rebuild replaces every row and hidden-ness belongs to the row — without that a rename mid-search restores the whole tree.
- **A "one-time migration" needs something that makes it one-time**, and `if not dest.exists()` is not it. `get_history_dir` ran its `~/.musickey` import on every call (all four history operations go through it) and treated a missing file as "not imported yet" when it actually meant "the user deleted it" — so Delete in the History panel unlinked a session and the panel's own refresh copied it straight back, inside the same click. Guard with a marker file written even when there was nothing to import (`_MIGRATED_MARKER` in `src/renamer/history.py`), so the steady state is one `exists()` rather than a glob per call and a crash midway just retries. Note why it survived: a fresh install has no `~/.musickey`, so the whole path is dead code on a clean machine — and any test that trusts the real `Path.home()` inherits whatever the developer happens to have.
- **When a fix makes an intermittent failure rarer without changing its signature, the surviving passes are the evidence.** Two rounds of raising a timeout took a Windows failure from 3-of-3 to 6-of-8, which felt like progress and was not — the signature never moved. What ended it was comparing a clean run against a failing one on the same machine minutes apart: the difference was *exactly one timeout*, which proved the process was not starved and the fault was local to one connection. That comparison is only available once a failure is intermittent, so the rarer-but-identical state is the one to exploit rather than to keep pushing on. Corollary to the entry below.
- **Don't drive `SingleInstance.send()` against a live primary in the same process** — use `hand_off` (`tests/gui/test_single_instance.py`), as every test there now does. On Windows that one connection is intermittently never serviced: 6 of 8 full-suite runs failed with `36 of 36 bytes still queued after 12000 ms`, load-sensitive in whether it fires but absolute when it does, under both a `qtbot.wait` spin and a real `QEventLoop`. It is local to the connection, not the process — a failing run is longer than a clean one by exactly the timeout, so everything else runs at normal speed around it. Raising the budget was the wrong instinct twice; the `N of M bytes` in the log is what settles it, since a whole frame still queued means the primary never read at all and no budget helps. The real cross-process path is `scripts/race_check.py`'s job, and one process was always a model of it.
- **Never join a worker thread from the thread whose event loop it needs**, and never stop pumping while it runs. `tests/gui/test_single_instance.py::run_off_the_main_thread` pumped with `qtbot.waitUntil` and then joined with `thread.wait()` (which does not pump), so the moment the worker was late the loop stopped — and since a Windows named-pipe write completes only once the server end reads, the join was waiting for a thread waiting for the join to stop. Pump in one loop, keep pumping through an overrun so the worker unwinds, and only then join. The diagnostic lesson is bigger than the fix: the abandoned worker still held the 30s `WRITE_TIMEOUT_MS` and logged `Timed out handing files` half a minute later **against whichever test was running by then** — so a stray log line does not belong to the test it is printed under once threads outlive tests, and a test that inherits a production timeout inherits that whole failure mode.
- **A test that waits for "no worker" is satisfied by the state *before* one starts.** `waitUntil(lambda: panel._art_thread is None)` right after asking for a load returns instantly — the debounce timer has not fired yet — and every assertion after it runs against an empty result. Waiting for the worker to *appear* first races the timer the other way. Do neither: stop the debounce and call the load method directly, so the reference exists before the wait begins (`pump_art` in `tests/gui/test_player_artwork.py`). Same family as the entry above about `rowAt()` and scroll ranges: **anything Qt computes lazily from layout is stale until the event loop has run**, so a test that scrolls and then asks what is visible gets the previous answer — wait *first*, not last. And note `add_tracks` leaves the view at the **end** of the list (auto-scroll on add), so a test looking for unread rows scrolls *up*.
- **Three Qt calls that run *other people's code* in the middle of yours.** `QProgressDialog.setValue()` **pumps the event loop**, so a worker's `finished` can be delivered from inside your progress callback — the Player's batch lookup closed its dialog and cleared the attribute there, and the very next line in the callback ran against the `None` it had just been assigned. Set the label first, the value last, and put nothing after it; then defer whatever the terminal handler does to `QTimer.singleShot(0, …)`, which is the same rule already stated above for modals fired from a drop or drag handler, arriving from a third direction. Related: **`isVisible()` is False for every widget in a dialog once `exec()` has returned** — which is exactly when a caller reads the user's answer out of it. Keying "is the artwork row part of this dialog?" off `isVisible()` meant approved cover art was silently never written; `isHidden()` is the question that survives the dialog closing. (Third guise of the same trap: not on screen ≠ not switched on.)
- **`QMenu.exec` cannot be monkeypatched out — PySide6 resolves it through C++.** A test that drives a context-menu handler therefore opens a real modal menu and hangs the whole suite *with no output at all* (the tell is `This plugin does not support grabbing the keyboard` before the silence). `setattr` on the type neither raises nor takes effect. Split menu construction from menu execution — `PlayerPanel._build_row_menu` returns `(menu, {name: action})` and the handler execs it and dispatches by name — so a test can ask what a row offers without showing anything.
- **`qtbot.wait(0)` does not drain the event queue**: a test that uses it to "let the deferred dialog run" asserts against a prompt that never fired and passes for the wrong reason. Use `qtbot.wait(10)` (see the `pump()` helpers) or `qtbot.waitUntil` on the effect.
- **An unclicked modal hangs the whole suite**: `tests/gui/conftest.py::duplicate_prompt_guard` replaces the duplicate prompt with a recorder that answers Cancel and then fails the test naming the collision, so a stray prompt is a readable failure instead of a hang. It also pins `duplicate_policy` to the shipped default, since it is a user setting the suite must not inherit. A test that means to reach the box patches `duplicate_policy._prompt` itself.
- **A debounced write resolves its destination when it *fires*, not when it was armed — so a pending one that outlives its widget lands wherever the process is pointing by then.** `PlayerPanel`'s column save is a 600 ms single-shot timer whose `_save_column_state` calls `load_config()`, i.e. `get_app_data_dir()`, at fire time. In the app that is merely a late write. Under `isolated_app_data`, which hands **every test its own throwaway directory**, it is one test's column layout landing in the *next* test's config — which the next `PlayerPanel` then restores instead of applying the shipped defaults. That is the whole of `test_player_column_order`'s intermittent failure, sighted 2026-08-13, -22 and -23 and never reproducible, because it needs a test that arms the timer followed by one slow enough to let 600 ms elapse. It was diagnosable only because a previous sighting had added a `why(player)` dump to the assertion: `defaults_version=3` and `wearing the shipped defaults: False` on what should have been a virgin config says the write happened *before* the test built anything, which no amount of staring at a truncated list-diff could have said. Two things about the fix. `closeEvent` **flushes** rather than cancels — a width changed in the last 600 ms before closing is a real change, and cancelling would silently drop it — and pytest-qt's cleanup calls `close()` on every `addWidget` widget, which is what makes the suite deterministic. And it is tested as an **invariant** (`isActive()` is False after `close()`), never by racing the timer, which is the only kind of assertion worth writing for a fault this shape. The general rule is the sibling of the two `get_app_data_dir` entries below: **anything deferred that reads process-global state must be flushed or cancelled at teardown**, because "which directory are we" is not captured when the work is scheduled.
- **The suite is isolated from the developer's own machine, and must stay that way**: `tests/conftest.py::isolated_app_data` (autouse) repoints `get_app_data_dir` at a throwaway directory, so `config.json`, `library.db` and the histories are per-test. Without it a test that reaches `load_config()` reads whatever was last chosen in Settings — which is how three `test_player_header_layout` tests passed here and failed on a fresh checkout. To give a widget a setting, build an `AppConfig` and `save_config()` it *before* constructing the widget; don't patch `load_config`, since a widget that imports it at module level has bound its own copy (see the next entry).
- **Don't read a user setting via `from … import helper` at a call site**: the name binds into the importing module, so patching it on the defining module has no effect and a test silently exercises the developer's own config. `resolve_additions` reads `duplicate_policy` itself for exactly this reason. The rule covers **`get_app_data_dir` above all**, because that is the one the whole suite's isolation hangs off: `tests/conftest.py::isolated_app_data` patches it on `src.utils.app_dirs`, so *every* caller must import it inside the function that needs it, and one that binds it at module scope silently opts out of the sandbox. `single_instance.py` did, from the day it shipped — the single-instance tests took their `flock` files in the developer's **real** `~/Library/Application Support/MixedInP` instead of the throwaway directory, and **3336** of them had accumulated there before anyone looked. Nothing user-facing broke (the names carry a pid, so they never collide), which is exactly why it survived: the only symptom was litter in a directory nobody lists. Two things worth copying from the fix. It is guarded by asserting **the binding, not the behaviour** — `assert not hasattr(single_instance, "get_app_data_dir")` fails on the very line someone would write to reintroduce it, where a test that watches for a file in the wrong place has to know which wrong place. And the behavioural test beside it globs the isolated directory rather than naming the file, because the lock carries the *scoped* name (user and session), not the bare app id. Note also that a half-done mutation check proves nothing here: adding the module-level import back while the function-local one is still there changes nothing, because the local import shadows it — remove both halves or the test passes against the bug.
- **`#:` comments become translator guidance**: lupdate harvests a `#:`-prefixed comment as an `extracomment` and staples it onto the next translatable string, so internal implementation notes end up as instructions to translators. Use plain `#` in any file containing `tr()` strings.
- **A `QMessageBox` button with custom text clips its own label**: the stylesheet's `padding: 8px 16px` on `QPushButton` is invisible to the native size hint, so any label wider than the 80px `QDialogButtonBox QPushButton` minimum is drawn into a contents rect narrower than the text — and QMessageBox centres rather than elides, so it's cut off at *both* ends ("kip Duplicate"). Boxes built from standard buttons are short enough to escape it. Size such buttons from their own font metrics, not a constant, because the labels get translated — see `_fit_buttons` in `dialogs/duplicate_policy.py`.
- **A `%n` plural's *source text* is what English ships**, so "Applied %n field(s) from Discogs" reaches the default language as "Applied 5 field(s)". `en` has no `.qm` by design — it *is* the source — so every `%n` string in the app renders its own `(s)` spelling to most users. Spelling the two forms out instead (`compatible_panel._sync_seed_label`) fixes English and breaks **ru/pl**, which need a third form for 2–4, i.e. the commonest counts; there is no wording that is right in both directions. So before reaching for a plural, ask whether the count is load-bearing at all — the Metadata panel's provenance line dropped it (`Applied from Discogs`) and is correct in all twelve languages, because the form beside it already shows every value that changed.
- **`pyside6-lupdate` only marks `%n` plurals for `tr()`, not for `QCoreApplication.translate()`**: a module-level function using `translate()` with a count silently ships a string no translator can give plural forms for. Host such strings on a `QObject` so `self.tr(src, "", n)` applies — see `DuplicatePrompt` in `dialogs/duplicate_policy.py`.

## UI copy

- **A tooltip is a reminder, not the manual.** Keep it to roughly one line — what the control does, plus a before/after example where that is the shortest possible explanation (see Space Dashes in `rename_panel.py`). Edge cases and rationale go in the docs, not the hover. Every extra sentence is also a sentence to translate into 11 languages.
- **A toggle's tooltip says what the next click will do**, in both directions, and updates with the state — a checked button alone doesn't convey that Playlists *replaces* the nav rail rather than opening a panel. See `Sidebar._sync_playlists_tooltip` and the collapse chevron in `set_collapsed`.

## Internationalization (i18n)

The GUI is translatable via Qt's native translation system. Language is chosen
in Settings and applied on restart (a `QTranslator` is installed at startup in
`src/gui/app.py:install_translators`). The selectable languages live in
`src/utils/i18n.py` (`LANGUAGES`); translation files are in
`src/gui/translations/` (`.ts` = source, `.qm` = compiled/bundled).

**When adding or changing any user-facing GUI string, you MUST:**

1. **Wrap it for translation.** Never add a bare user-visible literal.
   - Inside a `QObject`/widget instance method: `self.tr("Text")`.
   - At class-body / module level / `@staticmethod` (no widget `self`):
     `QCoreApplication.translate("ClassName", "Text")`.
   - For a literal that must be defined away from where it's displayed (e.g. a
     module-level field-label list): mark with `QT_TRANSLATE_NOOP("Ctx", "Text")`
     and wrap with `self.tr(...)` at the display site. See `metadata_panel.py`.
2. **Refresh the translation files** after adding/removing strings:
   `python scripts/build_translations.py` (runs lupdate to extract new strings
   into every `.ts`, then lrelease to recompile the `.qm`). This preserves
   existing translations and is the only way new strings reach Qt Linguist.
3. **Re-translate any string you EDIT, not just new ones.** Qt keys a
   translation by its exact source text, so changing an existing `tr()` string
   (even one character) breaks the key: lupdate marks the old translation
   `vanished` and re-adds the changed source as `unfinished`, dropping that
   string to **English in every language** until it's re-authored. The build
   script prints an "Untranslated strings" summary at the end (and
   `--strict` exits non-zero) so this regression is caught here, not in the
   running app — read it after every string change. The old text survives in
   the `vanished` entry of each `.ts`, so an edit can usually be recovered and
   spliced rather than re-translated from scratch. Two habits avoid the churn:
   settle the English copy *before* translating, and keep translatable text in
   small, granular `tr()` strings (not one big block per screen) so an edit
   orphans only the part that changed.

**The context argument must be a literal.** `QCoreApplication.translate(_CTX, "…")`
with a module constant extracts **nothing** — lupdate parses the source text and
cannot resolve a variable — so every such string falls back to English in all
eleven languages with no warning anywhere. `src/gui/lookup_flow.py` spells
`"LookupFlow"` out at all eight call sites for this reason.

**Do NOT wrap** (these are data/config, not UI prose): musical note names and
key codes (e.g. "8A", "C#m"), audio format codes used as logic values ("WAV",
"MP3"), tag/dict keys, `setObjectName(...)` selectors, stylesheet strings,
file-glob filter strings, and `logger`/`print` messages.

### Translation glossary (term handling per language)

When translating the `.ts` files, follow these term rules. Action buttons and
titles use the infinitive/command verb form (e.g. "Renombrar", "Renommer",
"Переименовать"); feature-list labels use noun phrases. Match Apple's localized
UI conventions for each language.

- **Keep in English in ALL languages**: `BPM`, `beat tracking`, `Chroma`,
  harmonic key codes (1A–12B / 1A–12A) and note names, and audio format codes
  (`WAV`, `MP3`, `FLAC`, `AIFF`, `M4A`, `OGG`). Also the product name
  "Mixed in P" and units (`dB`, `kHz`, `Hz`).
- **`sample`, `slicer`**: keep in English for Latin-script languages (es, fr,
  pt_BR, …); use native script for Cyrillic/non-Latin (ru: слайсер/сэмпл) so a
  Cyrillic UI stays consistent. (NB: "Sample Rate"/"Sample rate" is the DSP term
  and IS translated normally — it is not the producer "sample".)
- **`pipeline`**: the loanword in every Latin-script language (es/fr/it/pt_BR),
  `пайплайн` in ru, `流水线` in zh_CN, `potok` in pl. It shipped as
  "chain" in six languages (es *cadena*, fr *chaîne*, it *catena*, pt_BR
  *cadeia*, ru *цепочка*, pl *łańcuch*) and that was **wrong in three separate
  ways**, which is why it must not be "corrected" back. A chain is rigid links,
  so it loses the liquid-through-a-pipe image the feature is named for; *cadena*
  and *catena* read first as **assembly line** (*cadena de montaje*), which is
  the factory connotation rather than the flow one; and pt_BR *cadeia*
  colloquially means **jail**. All four languages' own tech communities use
  "pipeline" untranslated anyway. The decisive one is the **surf** reading —
  Banzai Pipeline keeps its English name in every one of these languages, and
  the step toggle is literally the tsunami hazard sign, so translating the word
  is what breaks the symbol. Two deliberate exceptions: **pl `potok`**, which
  beats the loanword because it is simultaneously the established Polish CS
  term *and* literally a stream of water; and **zh_CN `流水线`**, kept because
  its characters already read "flowing-water line". ru's button is the noun
  `Запуск пайплайна`, not the infinitive the rule above asks for, because
  `Запустить пайплайн` measures 164px against the button's 160px minimum.
- **`stream`**: translate in **every** language, as an ordinary noun for the
  look — a flowing ribbon of liquid (de `Strom`, fr `flux`, ru `поток`, ja
  `流れ`, zh_CN `水流`) — with the "Backdrop" half done exactly as its six
  sibling menu entries already do it (de `Hintergrund:`, ru `Фон:`, ja `背景：`
  …). This **reverses** the ruling the visual shipped under: it was
  `Silly Scope`, kept in English everywhere as a proper name and a pun on
  "oscilloscope", the same class as the product name. Renaming it to fit the
  look retired the pun, and with it the only reason not to translate — so do
  not "restore" the English-everywhere rule from the `vanished` entries, which
  is what a translator reading the old `<translatorcomment>` would do. The
  rename cost exactly one string in eleven languages, because the label was
  the only place the name reached the user; every other spelling of it was an
  identifier, and none of those was ever persisted (see the persisted-enum
  entry under Technical Considerations).
- **`Send To`**: retired from the UI (the step toggles replaced it); the rule
  it illustrated stands for any such phrase — localize in ALL languages
  (es "Enviar a", fr "Envoyer vers", ru "Отправить в") rather than leaving a
  Latin island in an otherwise localized UI.

Per-string changes during a translation audit get a `<translatorcomment>` noting
the reason; never use raw XML `<!-- -->` comments (lupdate strips them).

Untranslated strings always fall back to the English source, so a
partly-translated language is safe to ship. CLI strings (`src/cli.py`) are
intentionally left English-only. Full background: `src/gui/translations/README.md`.
